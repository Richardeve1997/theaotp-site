AI Engineering 101 · Field notes

Building the agent is the cheap part.

Two days of AI training in Sydney, one for business users and one for engineers, pointed at the same conclusion from opposite directions. You can ship an agent in an afternoon. What costs you is everything after: knowing whether it works, knowing when it breaks, and being able to prove either.

Delivered by Cognitivo, UNSW and the Macquarie University Centre for Applied AI. Sponsored by Gigabyte, NVIDIA and LangChain. UNSW CBD Campus, Sydney, 29 and 30 July 2026. Speakers included Dr Haritha Thilakarathne (NVIDIA), Faisal Masood (LangChain), Jake Broekhuizen (LangChain), Aadhar Bhardwaj (Cognitivo) and Vito Chen (Gigabyte).

These are my own notes on what transfers, written up for anyone deciding what to take from an event like this. Vendor slide decks are not reproduced here. The two workshop repositories are public and linked below.

The through-line

Two audiences, one conclusion.

Day 1 put people with no coding background in front of a real API that spends real money. Day 2 took engineers through the parts of the stack that decide whether an agent survives contact with production. Neither day argued that evaluation matters. Both were built so you couldn't avoid noticing.

The framing talk traced software architecture from monoliths through to agents, and made two claims worth repeating. First, that SaaS as a category is under pressure from personal software individuals now assemble themselves. Second, that RAG is a stepping stone rather than a destination: useful, but bounded by what retrieval can reach. The rest of the day was constructed so participants felt both rather than accepted them on authority.

Day 1 · Building with AI

Ship a real app in a single day.

Fifty business users, no coding background, one working internet-reachable web app each with an AI agent inside it. The exercise was the buyer side of a simulated furniture marketplace: a real catalogue of 762 products, a real per-user balance, and an ordering system that genuinely debits it.

LevelWhat it required
Level 1A normal web app: entity model, UI, login, database persistence, workflow logic, reports, and the local instance exposed to the internet through a tunnel.
Level 2External APIs: email, calendar invites, transcription, LLM calls for generation and summarisation, basic context engineering, inbound webhooks.
Level 3An in-app agent. Turn the API into a tool menu so plain-English requests just work.
Level 4Stretch: vector RAG over the catalogue for open-ended product questions.

What actually transfers

  • Plan in files before building. Participants had the assistant produce a CLAUDE.md of standing instructions, a requirements.md, an architecture.md holding the data model, and technical specs, all before meaningful code existed. CLAUDE.md is read at the start of every session, so it is where durable rules belong. Describe the goal, not the implementation, and keep each ask small.
  • Sketch the entity model first. Get the model to describe what the app must remember, customer, product, order, as a diagram plus a plain-English explanation. Read the explanation, not the diagram syntax. Confirming that before scaffolding was presented as the highest-leverage few minutes of the day.
  • Tool descriptions are the product. This was the conceptual centre. Nobody was handed a ready-made agent. The exercise was to name the four available actions and write an honest one-sentence description of when to use each. The failure mode is explicit: the catalogue search does exact category matching only, so a description that overpromises gets you a confident wrong answer instead of a clean failure. Reasoning the API cannot do, "cheap", a colour, a vibe, has to happen in the agent over plain results.
  • Confirm before spending. Placing an order really debits a real balance, so the agent had to show what it was about to buy and wait. Treat that as a default for anything that spends money, sends something externally, or is hard to reverse. Not a hardening step you add later.
  • Failures are conversations, not stack traces. Insufficient balance and missing products had to be explained back in plain language with a suggested next step. Participants were then told to deliberately break their own app, overspend, request nonexistent products, double-click buy, before the showcase.
  • Secrets from the first commit. Repos were public, so the guides walked through environment variables and a gitignored .env, then had everyone run git status and confirm it did not appear. Small, taught deliberately.

The optional stretch

The vector RAG task is a genuinely good teaching artefact. It explains chunking, embedding, storage, retrieval and generation in plain terms, then points out that for 762 products a dedicated vector database is unnecessary: embeddings fit in memory and cosine similarity over a list is enough. It also insists you test retrieval on its own, printing which chunks came back and checking them by eye, before wiring up generation. That discipline transfers to any RAG work.

The second was OpenClaw, an open-source personal agent that runs on your own machine and acts through apps you already use. Participants packaged their four shop tools as an OpenClaw skill. The guide carries a pointed safety note: it is not sandboxed the way an in-app agent is, it takes real actions on a real machine and a real account, and it should be granted the one skill it needs rather than every permission it offers.

Day 2 · AI engineering foundations

What decides whether it survives production.

Thirty-five engineers, four sessions, two of them long hands-on workshops. Infrastructure and hosting economics, then a fireside on owning your own intelligence, then the two blocks that mattered: evaluation and the agent lifecycle.

Infrastructure

LLM hosting pathways and the cost implications of each, clustering, environment setup, and hosting foundation models with vLLM and LiteLLM alongside RAG. One pattern worth stealing regardless of hardware: participants reached shared GPU boxes over SSH through Cloudflare Access, which puts authenticated access to expensive shared machines behind an identity provider instead of exposed SSH.

Evaluation, and why it is a commercial decision

The case made was not academic. Evaluation drives which model you pick, whether to fine-tune at all, which prompt strategy you standardise on, cloud versus on-premises, your safety and bias posture, and when to retrain. Without a baseline you cannot tell whether a model swap, a prompt change or a fine-tune helped, and the answer is never obvious from spot-checking.

Evaluation splits three ways. Controlled: automated benchmarking on standard datasets, plus synthetic and adversarial cases you generate to stress-test behaviour. Human-centred: expert review where tone and nuance matter, plus crowdsourced assessment for breadth. Field: production monitoring, A/B testing, log analysis and live feedback.

The metric taxonomy runs from accuracy, precision, recall and F1, through perplexity and n-gram overlap measures like BLEU and ROUGE, to academic benchmarks such as GLUE, SuperGLUE, SQuAD, MMLU and GSM8K. The qualitative side is LLM-as-a-judge, pairwise comparison, coherence and relevance ratings, consistency across similar inputs, and bias checks. Runs were tracked in MLflow, with Weights & Biases as the alternative.

Customisation, in order of cost

The spectrum runs pre-training, continued pre-training, supervised and domain-adaptive fine-tuning, preference alignment, RAG, and in-context learning. The practical guidance for anyone not training foundation models: try in-context learning first, and if you do fine-tune, keep the backbone frozen and inject a small trainable set. LoRA for dense updates, adapters for modularity, prefix tuning for prompt-like control. Expect trainable parameters around 0.1 to 1 percent of the full model, use a higher learning rate than full fine-tuning (roughly 1e-4 to 1e-3), and monitor a held-out set to avoid over-adapting.

Two details worth carrying from the lab, because they only surface when you run things locally. The same running container served as both the model under test and the judge, which is fine for a demo and explicitly flagged as not a production judging setup. And fine-tuning had to stop the inference container first, because the serving runtime reserves most of the box.

The agent development lifecycle

Build, test, deploy, monitor in sequence for any single change, with iterate and govern running continuously across all of them.

The build argument is the one to internalise. A chain is inflexible: a vanilla RAG pipeline has no answer when the search step returns irrelevant results. A plain ReAct agent is flexible but unreliable, failing through task ambiguity, inconsistent tool use, over-reliance on internal knowledge, and getting lost in long history. The resolution is developer-defined control flow where you need determinism, and agentic autonomy only where flexibility genuinely earns its keep.

Middleware is the mechanism. Hooks wrapping the core agent loop that add human-in-the-loop approval, summarisation to prevent context overflow, PII redaction, retry with backoff, and model fallback, without rewriting the agent. Treat it as part of the agent, not infrastructure bolted on afterwards.

The loop

Offline and online feed each other.

You can prototype an agent in an afternoon, but the space of possible failures is vast and cannot be predicted upfront. Models are non-deterministic and constantly changing, fixes cause regressions, tool calls fail, user input is unbounded, and small early mistakes cascade.

Two evaluator types: deterministic code evaluators for structured output, LLM-as-judge for unstructured. Two paradigms: offline evaluation against known ground truths before deployment, and online evaluation on live traces where no ground truth exists, checking helpfulness, policy violations, PII exposure and tone.

online eval surfaces an issue ↓ becomes an offline test case ↓ offline eval validates the fix ↓ online eval confirms it in prod ↺

Annotation queues sit in the middle, so humans review flagged traces, correct outputs, and promote validated examples into the evaluation dataset. That is what stops the dataset going stale while the product moves.

Reference code

Two repositories worth reading.

Both public. Both short enough to read in a sitting, which is the main reason to bother with them.

langchain-basics

An async support agent over the Chinook sample music database. Seven tools grouped by capability: music discovery, account support, long-term memory, and delegated LLM reasoning. The most instructive file is the authorisation middleware, which blocks anonymous access to account tools and stops a customer reading another customer's invoice, short-circuiting before the tool ever runs, with the same check repeated inside the tool as defence in depth. Long-term memories are namespaced per customer so they persist across threads without leaking between them.

The evaluation suite is the other reason to read it: offline it scores tool trajectory, required output, data leakage, PII, correctness and conciseness; online it checks live traces for the same concerns.

github.com/masoodfaisal/langchain-basics ↗

llm-eval-nim-demo

Evaluating and improving a model for a specialised domain, legal Q&A, running entirely on one machine. Notebook 01 deploys a local NIM and evaluates it on GSM8K with LLM-as-judge and ELO ranking. Notebook 02 does the domain evaluation, comparing zero-shot against in-context learning using BLEU, ROUGE and token F1 plus a judge scoring against a rubric. Notebook 03 LoRA fine-tunes and compares the adapted model against the same base weights on the same held-out rows.

That last part is the bit to copy. Comparing against the same base weights on the same held-out set is the correct control, and it is easy to get wrong in a way that flatters your fine-tune.

github.com/haritha91/llm-eval-nim-demo ↗
If you take five things

What I'd actually act on.

  • Write tool descriptions like API docs for a new hire. Make them honest about what the underlying system cannot do. Overpromising converts a clean failure into a confident wrong answer, which is far harder to detect.
  • Put a confirmation step in front of anything hard to reverse. Spending money, sending externally, deleting. Default, not hardening.
  • Get an evaluation dataset in place early, even a tiny one. Without a baseline you are guessing about every change you make afterwards.
  • Prefer in-context learning before fine-tuning. If you do fine-tune, use a parameter-efficient method and compare against the same base weights on the same held-out set.
  • Treat middleware as part of the agent. Authorisation, PII redaction, approval gates, retries, fallbacks. Not infrastructure you add once something goes wrong.

One meta-observation. Day 1 put non-engineers in front of a real API that spends real money, and the guides carried the safety thinking rather than the tooling: confirm before spending, handle failure gracefully, keep the key out of the repo, grant only the permission you need. That is a reasonable model for how to onboard non-engineers onto agent tooling anywhere.
