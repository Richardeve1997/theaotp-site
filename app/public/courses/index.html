The six scenarios

  • Customer support resolution agent. An Agent SDK agent with MCP tools for customers, orders and refunds, aiming for 80% first-contact resolution and knowing when to hand over to a person.
  • Code generation with Claude Code. Custom slash commands, CLAUDE.md files, and when to use plan mode instead of direct execution.
  • Multi-agent research system. A coordinator that hands work to subagents for search, document analysis, synthesis and cited reports.
  • Developer productivity with Claude. An agent that helps engineers explore unfamiliar codebases using the built-in tools and MCP servers.
  • Claude Code for continuous integration. Automated code reviews, generated tests and pull request feedback that's useful and low on false positives.
  • Structured data extraction. Pulling information out of messy documents, checking it against JSON schemas and handling the edge cases.

The guide's ideal candidate is a solution architect with six or more months of hands-on work across the Claude API, the Agent SDK, Claude Code and MCP.

07Study notes

Study notes, domain by domain.

Five domains. The bigger the weight, the more questions. Here's what each one tests, in plain English.

Domain 1 · 27% of the exam

Agentic architecture and orchestration. How an agent loop runs, and how a coordinator manages a team of subagents.

  • The loop. Send the request and read stop_reason. If it's "tool_use", run the tool and send the result back. If it's "end_turn", stop. Don't decide when to stop by reading the model's text, and don't rely on a turn limit as the main way to stop.
  • Subagents start blank. They don't inherit the coordinator's conversation, so put everything they need in their prompt. The coordinator spawns them with the Task tool, which has to be in its allowedTools. Several Task calls in one response run in parallel.
  • The coordinator owns the plan. All messages between subagents go through it. If it splits a topic too narrowly, the report misses whole areas even when every subagent does its job.
  • Code beats prompts for hard rules. When a rule must hold every time, like verifying the customer before a refund, enforce it with a hook or a prerequisite check. Prompt instructions still fail some of the time.
  • Hooks. PostToolUse hooks clean up tool results before the model sees them, for example turning mixed date formats into one. Hooks on outgoing calls can block a refund over a limit and route it to a person instead.
  • Fixed or adaptive plans. Use a fixed prompt chain for predictable work like a review, and let the plan adapt for open-ended investigation.
  • Sessions. --resume continues a named session and fork_session branches one. If the old tool results are stale, start fresh with a summary instead.

Domain 2 · 18% of the exam

Tool design and MCP integration. How the model picks tools, how tools report failure, and where MCP servers are configured.

  • The description is how the model chooses. Say what the tool does, what it takes, example queries, edge cases, and when to use it instead of a similar tool. If two tools overlap, rename or split them.
  • Structured errors. Use MCP's isError flag and say what kind of error it is (transient, validation, business rule or permission), whether a retry could work, and what happened in words. A generic "operation failed" leaves the agent guessing.
  • A failure isn't an empty result. A timeout needs a retry decision. A search that worked and found nothing is a valid answer.
  • Fewer tools per agent. Give each agent the four or five tools its role needs, not eighteen. tool_choice can be "auto", "any" (it must call some tool) or a named tool.
  • Where MCP servers live. Shared team servers go in the project's .mcp.json, with secrets pulled from environment variables like ${GITHUB_TOKEN}. Personal ones go in ~/.claude.json. Use an existing community server for standard tools like Jira, and build your own only for team-specific work.
  • Built-in tools. Grep searches file contents, Glob finds files by name or pattern, Edit needs a unique text match, and Read plus Write is the fallback when Edit can't find one.

Domain 3 · 20% of the exam

Claude Code configuration and workflows. Where instructions, commands, skills and rules live, and how to run Claude Code in a pipeline.

  • The CLAUDE.md hierarchy. User level (~/.claude/CLAUDE.md) is yours alone and never reaches teammates. Project and directory files are shared through the repo. @import pulls in other files, and /memory shows what actually loaded.
  • Commands and skills. Project commands go in .claude/commands/ and are shared through version control. Personal ones go in ~/.claude/commands/. Skills live in .claude/skills/, and their frontmatter can set context: fork (run in isolation), allowed-tools and argument-hint. Skills load on demand, while CLAUDE.md is always loaded.
  • Path rules. Files in .claude/rules/ with a paths glob in their frontmatter, like **/*.test.tsx, only load when Claude edits matching files. They beat a CLAUDE.md per folder when the files are spread across the codebase.
  • Plan mode or direct execution. Plan mode suits big, multi-file changes with several valid approaches. A small fix with a clear stack trace can run directly. The Explore subagent keeps noisy discovery out of your main conversation.
  • Iterating. Two or three concrete input and output examples fix vague instructions. Write the tests first and share the failures. Ask Claude to interview you before it builds in an unfamiliar area.
  • In CI. claude -p runs without waiting for input. --output-format json with --json-schema gives findings you can post as pull request comments. A fresh instance reviews code better than the session that wrote it.

Domain 4 · 20% of the exam

Prompt engineering and structured output. How to get precise, consistent, machine-readable output.

  • Explicit criteria. "Be conservative" doesn't improve precision. Say exactly what to report and what to skip. If one category throws up false positives, switch it off while you fix it, because it drags down trust in the rest.
  • Few-shot examples. Two to four targeted examples for the ambiguous cases, showing the reasoning and the output format, do more for consistency than longer instructions.
  • Schema output. tool_use with a JSON schema is the most reliable way to get valid JSON. It fixes syntax, not meaning: totals can still fail to add up. Make fields nullable when the source might not have the answer, so the model doesn't invent one, and add "other" or "unclear" to enums.
  • Validation and retry. On a retry, send the document, the failed output and the specific error. Retrying won't help when the information isn't in the document.
  • Message Batches API. 50% cheaper, but results can take up to 24 hours with no latency guarantee, and it can't run tools mid-request. Use it for overnight reports and audits, never for a check that blocks a merge. custom_id matches results to requests.
  • Review in passes. Review each file on its own, then run a separate pass across files. A second, independent instance catches more than asking the same session to check itself.

Domain 5 · 15% of the exam

Context management and reliability. Keeping the facts straight over long runs, and knowing when to hand over to a person.

  • Protect the facts. Summaries blur numbers, dates and promises. Keep amounts, order numbers and statuses in a "case facts" block in every prompt, trim tool output to the fields that matter, and put key findings at the start, because findings in the middle of a long input can get missed.
  • Escalation. Hand over when the customer asks for a person, when policy doesn't cover the request, or when the agent can't make progress. Sentiment and the model's own confidence score are poor triggers. If a lookup returns several matching customers, ask for another identifier rather than guessing.
  • Errors across agents. Send the coordinator the failure type, what was tried, any partial results and possible alternatives. Hiding an error as an empty success and killing the whole run over one failure are both wrong.
  • Long sessions. Use scratchpad files for findings, subagents for exploration and /compact when context fills up. For crash recovery, each agent writes its state to a known file and the coordinator reloads it on resume.
  • Human review. 97% overall accuracy can hide poor results on one document type or field. Check accuracy by document type and field, sample high-confidence results at random, and send the low-confidence ones to people.
  • Sources. Keep each claim tied to its source through every summary. When two good sources disagree, report both and say where each came from, and include dates so an older figure doesn't read as a contradiction.
The guide also lists topics that won't be tested, including fine-tuning, API billing and authentication, computer use, vision, streaming, rate limits and pricing calculations, cloud provider setup, embeddings and vector databases, and tokenisation details. Spend your time elsewhere.

Four exercises from the guide

  • 1A multi-tool agent that escalates.Three or four MCP tools with clear descriptions, two of them deliberately similar. A loop driven by stop_reason, structured errors, a hook that blocks anything over a set amount and sends it to a person, and a test message with several problems in it.

  • 4A multi-agent research pipeline.A coordinator running at least two subagents in parallel, findings that keep their source and date, a simulated timeout that comes back as a structured error, and two sources that disagree, with both kept in the report.

Then the sample questions

Section 9 of the guide has twelve sample questions from four of the scenarios, each with why the right answer is right and why the others aren't. Do them after the exercises and read every explanation, including the ones you got right.

Checklist before you book

  • You can say what a loop does when stop_reason is "tool_use" and when it's "end_turn".
  • You know why a hook beats a prompt for a rule that must always hold.
  • You pass context to subagents on purpose, because they inherit nothing.
  • You can write a tool description that stops the model mixing up two similar tools.
  • Your tools return errors that say whether a retry could work.
  • You can put a command, skill, rule or MCP server at the right scope, personal or project.
  • You can choose plan mode or direct execution for a given change, and say why.
  • You can run Claude Code in CI with -p and get JSON out.
  • You can get schema-valid output with tool_use, and you know what the schema won't catch.
  • You know when the Batches API fits and when it doesn't.
  • You can name the right escalation triggers, and the two unreliable ones.
  • You can keep facts, sources and dates intact through a long or multi-agent run.
09What to do now

Pick your starting point.

You don't need all five. Start where you are and finish one this week.

  • If you've never built an app: start with 01. It's short, free during the beta, and you finish with two working apps.
  • If you run a business and want to know what agents can do for it: watch the free videos in 03. You'll learn how agents are put together, which makes it much easier to tell a real agent project from a demo.
  • If you already use Claude Code: do 02, then 05, so you can run longer jobs and prove they work.
  • If your company is a Claude partner: book the Architect exam once the four exercises in 08 feel easy and every line of the checklist is true.
  • If your company isn't a partner: do the prep courses anyway. The skills are the same, and Claude Academy gives you a certificate of completion.
