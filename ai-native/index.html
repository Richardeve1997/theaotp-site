00 · How to use this

01 · Foundation

Work starts and ends in a co-work agent tool.

Not just coding. Every piece of knowledge work begins inside an agent that can read your files, run your tools and finish the job, and it ends there too.

The tell of an AI native company is where a task lives. If the brief, the draft, the research and the final output all pass through an agentic tool like Claude Code, Codex or Cursor, the company has one place where work compounds. If people copy answers out of a chat window into a document, the AI is a helper, not the workplace.

Anthropic wrote up how their own teams do this, and the interesting part is that the legal, marketing and data teams show up alongside engineering.

02 · Foundation

Every function has its skills.

A skill is a written, reusable procedure an agent can load and follow. Marketing, sales, finance, ops and support each need a full set covering every workflow they run and every key output they produce.

Prompts get typed once and lost. A skill is a file in a folder: what the task is, how to do it, what good looks like, and any scripts or templates it needs. Once a function has its workflows written down this way, any person and any agent in the company can run them the same way. That is what turns individual AI use into company capability.

Anthropic's engineering post on Agent Skills is the clearest description of the format, and the same folder structure now works across most of the major agent tools.

03 · Foundation

One central knowledge base.

All of the company's structured data and unstructured data, in one place an agent can reach.

Structured means the tables: CRM, finance, product data. Unstructured means everything else: documents, Slack threads, email, PDFs, tickets. An AI native company has connected both into a single searchable layer, with the same permissions the source systems already enforce, so an agent answers from the company's actual context rather than from the model's general knowledge.

04 · Foundation

Specialised knowledge bases per team and project.

The central base is the source. Each team and each key project then gets its own scoped slice, because an agent with everything in context does worse than an agent with the right things.

Context is a budget. Pour the whole company into every request and the agent drowns in noise, costs more and answers worse. The fix is smaller knowledge bases carved from the central one: the sales team's, the onboarding project's, the pricing project's. Each holds what that work needs and nothing else, and each stays in sync with the master.

Anthropic's context engineering post explains why this matters at the level of the model, which is the argument you need when someone asks why one big base is not enough.

05 · Foundation

Skills and knowledge work in every tool.

Whatever AI tool someone opens, the company's skills and knowledge bases are already there, and passing them to a colleague takes seconds.

If a skill only works in one product, or the knowledge base only answers inside one chat window, you have built a silo with an AI label on it. AI native companies expose their knowledge and their tools through open connectors so Claude, ChatGPT, Cursor, Copilot and the internal agents all read from the same place. Sharing a skill with a teammate should be a file, not a training session.

06 · Keep it honest

Every use improves the agent.

A feedback loop: each time someone uses a skill or an agent, the correction they make gets written back into the skill, so the next run is better without anyone scheduling a rewrite.

Most companies improve their AI in big manual passes, if at all. The native version is continuous. The agent runs, a person corrects it, the correction becomes a line in the skill file or a new check in its evaluation, and the version number ticks up. Over a few months the skills reflect exactly how your company works, because your company taught them.

Google Research published the mechanism as a paper. It is the most concrete description I have found of an agent compiling its own experience into persistent knowledge.

07 · Keep it honest

Tests and evals define good output.

Every key workflow has a written definition of what good looks like and a set of checks that run against it. Without that, "the agent got better" is an opinion.

An eval is a list of real inputs with known good outputs, plus the rules an output has to satisfy: has a source, has the price, under two hundred words, whatever the workflow needs. Run it every time the skill changes. A failing check sends the output back for revision before a person ever sees it. This is the same discipline software teams already use for code, applied to the work the agents produce.

Anthropic's guide is written for people building agents, but the first half applies to any workflow you care about.

08 · Keep it honest

Cost and tokens are measured.

Token spend is tracked at the team level, the individual level, and for every critical high volume workflow. One monthly bill from the provider is not measurement.

Tokens are the new cloud bill, and they behave the same way: invisible until someone tags them. AI native companies tag every call with the team, the person, the workflow and the prompt version, so they can see that Tuesday was expensive and which agent step caused it. That is what makes efficiency work possible at all. You cannot shrink a cost you cannot attribute.

09 · Own it

Non-technical people build in a sandbox.

A democratised development process: the ops manager, not an engineer, can build a proof of concept product, inside a sandbox that has governance and guardrails already built in.

The blocker is never whether a non-engineer can build something with AI now. They can. The blocker is whether the company has a safe place for them to do it: approved models, scoped data access, an audit log, and a quick way to deploy an internal tool without a ticket. Put the rails in and the proofs of concept appear on their own. Leave them out and either nothing ships or something ships that should not have.

Shopify has done this at company scale. The write-up covers their LLM proxy, the drag-and-drop deployment tool, and the fact that non-engineers needed different tools from engineers.

10 · Own it

Own your intelligence.

For the high volume, critical workflows that give you a competitive advantage, you have started fine-tuning open source models on your own first-party data.

Renting a frontier model is the right default for almost everything. But a small number of workflows are the business: the ones that run thousands of times a day and encode how your company does the thing better than competitors. For those, a fine-tuned open model trained on your data is cheaper per call, faster, and yours. Nobody can price it up or switch it off, and it keeps learning from data nobody else has.

Meta's Llama fine-tuning guide is the practical starting point: what the methods are, how much data you actually need, and how to run it.

11 · What to do now

Pick the lowest number you scored no on.

Reading ten links changes nothing. Fixing the first gap on the list changes how every item after it works.

  • If your team still copies answers out of a chat window: start at 01. Move one real workflow into an agentic tool this week and do not move it back.
  • If you have the tool but every prompt is typed fresh: 02, then 06. Write the first skill, then make correcting it the habit.
  • If the agents keep answering from general knowledge: 03, 04 and 05. Connect the data, scope it, and make it reachable from every tool.
  • If it works but nobody can prove it: 07 and 08. Evals and cost tracking are how you keep the budget next year.
  • If you have all of that: 09 and 10. Open the sandbox to the whole company, then pick the one workflow worth owning outright.

If your company is not moving on seven through ten soon, I would be concerned. Those are the ones that take longest to build and are hardest to buy.
