02 On Opus 5.5

What he said about Opus 5.5.

On launch day he called it "a really good model" and said it had been his daily driver for weeks.

  • 1A full C to Rust port, head to head.His team had Opus 5.5 and Fable 5.1 each port HAProxy from C to Rust. Both passed nearly all of HAProxy's tests. Opus 5.5 finished in 9.5 hours against Fable 5.1's 12, for 51% less cost.
  • 2Formal verification from a couple of prompts.He used Opus 5.5 to formally verify the Claude Agent SDK in Lean. A couple of short prompts produced 16 PRs fixing bugs and race conditions. He says he doesn't know Lean or TLA+ well, but Claude is excellent at both, and he sometimes combines the two to hunt for data flow, concurrency and state bugs.

03 The five steps

The workflow from the Reel.

The idea behind all five: set Claude up so it can do the work without you checking in all the time.

That line is Boris's, from the Claude interview, and so is the reason it works on harder jobs: "it can verify its work." Here are the five steps, each with where it comes from.

  • 1Describe the objective with /goal.Say what done looks like and what good looks like. The docs say /goal "sets a completion condition and Claude keeps working toward it without you prompting each step." A good condition has one measurable end state, a stated check, and the constraints that matter. Their example is /goal all tests in test/auth pass and the lint step is clean.
  • 2Give Claude a way to test its own work.This is the one he calls the most important. In his thread: "If Claude has that feedback loop, it will 2-3x the quality of the final result." He has Claude test every change to claude.ai/code in a real browser through the Claude Chrome extension. For you that might be a test suite, a bash command, a browser or a phone simulator.
  • 3Turn on auto mode.Auto mode lets Claude run without routine permission prompts. A separate classifier reviews each action before it runs and blocks anything that goes beyond your request. At YC he said Opus 5 with auto mode "can go for days, weeks, months at a time."
  • 4Turn every mistake into a rule.His team shares one CLAUDE.md for the Claude Code repo, checked into git, and everyone adds to it several times a week. Any time Claude does something wrong, it goes in the file so Claude doesn't do it next time. In code review he tags Claude on teammates' PRs to add the lesson as part of the PR.
  • 5Break a big task into chunks.Give each chunk its own goal so a mistake early on doesn't compound across a long run. This one is my own advice, not a Boris quote. The closest thing he describes is dynamic workflows, which split one big task into stages of agents that do the work, then verify it, then fan out again.

04 Delete, then add back

They deleted 80% of the system prompt.

With every new model the team deletes most of Claude Code's prompt and adds lines back only when they prove they're needed.

For Opus 5 they cut 80% of it. A lot of the old prompt was correcting for things earlier models got wrong, and Opus 5 just does them. He calls the method an ablation: delete the whole system prompt, then bring it back line by line to measure what each line does. Their own tests found the model is a little smarter without the prompts, though the product still needs some of them to behave well for people.

His advice for anyone using Claude Code: every six months, delete your CLAUDE.md, your skills and your hooks, and see what the model does. Then rebuild piece by piece. Use it, watch where it stumbles, and only when it stumbles on the same thing repeatedly do you add an instruction back, because the model reads that instruction every single time.

This sits fine next to step 4. The rules in a shared CLAUDE.md are worth keeping while the model needs them. When a new model arrives, test whether it still does.
05 How they prompt now

Harder tasks, fewer instructions.

The common mistake he sees is over-specific instructions: do one, then two, then three, then four.

  • 1Go higher level.Describe the task, the guardrails and the exit criteria, then let the model work and come back later. Give it a task slightly harder than you think it can do.
  • 2Verification matters most.He says the skill now is less prompt engineering and more giving Claude a hard task plus a way to verify its work along the way, which he calls "probably the single most important thing" people get wrong.
  • 3A real example.His prompt to rewrite the Claude desktop app from Electron to Swift: run the Electron app in a Mac virtual machine, screenshot it, compare it pixel by pixel to the Swift version, and don't stop until done. At the time of the talk it had been running for about two weeks.
  • 4Bigger rewrites.A teammate had Claude rewrite Bun, the runtime Claude Code is built on, from Zig to Rust. One dynamic workflow, some steering, 11 days. It's in production now.
  • 5The tools still help.He says you don't strictly need /goal or /loop with Opus 5, "these help", but what you really need is the task and a way to check the output.
06 At team scale

Claude maintains its own code.

The Claude Code team runs 20 or 30 routines a day across its code bases, each started from a one-sentence prompt.

A routine is a repeating task. A loop runs it locally on a schedule, and a routine runs it in the cloud so you can close your laptop. Their routines clean up dead code, ship experiments that are already at 100%, write tests where coverage is thin, delete useless tests, and one he calls the abstraction police finds near-duplicate abstractions and unifies them. Each one opens a pull request. He says it's hundreds, sometimes thousands, of agents a day.

For one-off big jobs he uses dynamic workflows. You just tell Claude to "use a workflow", and it orchestrates many agents in stages inside a sandbox.

In the Claude interview he adds that in the product org, about 65% of pull requests are now written by Claude Tag (Claude working in Slack), and that you want it set up so you aren't checking in all the time.

07 His own setup

The January thread in one table.

He calls his setup "surprisingly vanilla". Here are the 13 tips, shortened.

TipWhat he does
1. ParallelRuns 5 Claudes in his terminal, tabs numbered 1 to 5, with system notifications when one needs input.
2. Web tooRuns 5 to 10 more on claude.ai/code, hands sessions between local and web, and starts some from his phone.
3. ModelUsed Opus 4.5 with thinking for everything at the time. Bigger and slower than Sonnet, but it needs less steering, so it ends up faster.
4. Shared CLAUDE.mdOne file for the repo, in git. Every mistake Claude makes gets added.
5. ReviewTags @.claude on PRs to update CLAUDE.md, via the Claude Code GitHub action.
6. Plan modeMost sessions start in Plan mode. Once the plan is good, Claude can usually do it in one shot.
7. Slash commandsOne for every inner-loop workflow, like /commit-push-pr, checked into .claude/commands/.
8. Subagentscode-simplifier and verify-app, among others.
9. HooksA PostToolUse hook formats Claude's code.
10. PermissionsNo --dangerously-skip-permissions. Pre-allows safe commands with /permissions, shared in settings.json.
11. ToolsSlack through MCP, BigQuery through the bq CLI, Sentry logs.
12. Long runsA background agent or Stop hook checks the work at the end. In a sandbox, permission prompts are off so Claude isn't blocked on him.
13. VerifyThe most important one: give Claude a way to verify its work.

08 What to do now

Pick one. Use it today.

Reading Boris won't change your output. Setting up one of these will.

  • If Claude keeps handing you broken work: start with step 2. Give it a test, a build or a browser it can check itself against.
  • If you babysit every session: write one /goal condition with a real check, and run it in auto mode.
  • If your CLAUDE.md is a year of patches: try his six-month reset. Delete it, use Opus 5.5 for a day, and add back only what it keeps getting wrong.
  • If you work on a team: share one CLAUDE.md in git and add a rule every time Claude makes a mistake.

See what's possible. Then build it.
